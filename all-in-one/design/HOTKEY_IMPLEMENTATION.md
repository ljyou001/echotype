# 快捷键与录音控制实现技术文档

## 核心挑战
在实现全局快捷键（特别是 Push-to-Talk 对讲机模式）时，我们遇到了以下核心技术挑战：

1. **组合键与单键的兼容性**：系统需要同时支持复杂的组合键（如 `Ctrl+Shift+Space`）和简单的单键（如 `CapsLock`, `RCtrl`）。
2. **KeyUp 事件缺失**：Electron 原生的 `globalShortcut` API 仅支持按下触发，无法检测按键松开。
3. **输入拦截（Swallowing）**：使用 Electron 注册快捷键时，系统原有的按键功能会被拦截（比如 `CapsLock` 无法切换大小写，`RCtrl` 无法作为修饰键使用）。
4. **监听器堆叠与双重触发**：在集成 `uiohook-napi` 后，若管理不当，会导致监听器在热重载或设置更改时累加，造成逻辑多次执行。
5. **状态同步竞态**：React 的渲染周期与原生键盘事件之间存在时间差，导致按键回调中可能读取到过时的配置状态（Stale Closure）。

## 尝试历史与演进

### 尝试 1：原生 `globalShortcut` + 定时器模拟
- **方案**：注册按下事件，并使用短暂定时器模拟录音。
- **结论**：**失败**。无法实现真正的“按住录音”，体验生硬，且由于拦截了单键导致系统输入不可读。

### 尝试 2：集成 `uiohook-napi` 基本模型
- **方案**：引入原生 C++ 模块监听系统的 `KeyDown` 和 `KeyUp`。
- **结论**：**部分成功**。实现了对讲机逻辑，但遇到了监听器无限累加的 Bug，导致按一次键产生数十个后台请求。

### 尝试 3：双驱动分流逻辑
- **方案**：让组合键走 Electron `globalShortcut`，单键走 `uiohook`。
- **结论**：**混乱**。两个驱动之间存在逻辑重叠，且重复注册导致状态混乱，依然存在“连接爆炸”的问题。

### 尝试 4：纯净单路监听 + Ref 状态同步 (当前生产方案)
- **核心逻辑**：
  - **Singleton 监听器**：在主进程生命周期内仅初始化一次全局监听实例。
  - **Uiohook 优先**：凡是 `uiohook-napi` 能处理的按键（单键或兼容组合键），一律禁用 Electron 的 `globalShortcut` 注册，防止劫持和干扰。
  - **Ref 状态锁**：在渲染进程中使用 `useRef` 动态追踪 `recordingMode`。
- **效果**：**成功**。解决了按键干扰，实现了精准的对讲机/开关切换，且后端稳定性极大提升。

## 已知问题与防御措施

| 问题现象 | 解决方案 | 状态 |
| :--- | :--- | :--- |
| **后端 ONNX 推理崩溃** | 增加 `totalSamples > 0` 过滤，拦截由于极快速点击产生的零字节数据包。 | ✅ 已防御 |
| **CapsLock 状态失效** | 采用 `uiohook` 非拦截监听，确保系统原有 KeyDown/Up 信号正常透传。 | ✅ 已解决 |
| **无限建立连接** | 监听器单例化 + 状态锁定，确保每次物理动作仅触发单次状态流转。 | ✅ 已解决 |

## 未来演进方向
- **硬件加速度计集成**：在移动端或特定外设上尝试非按键录音触发。
- **自定义静默延迟**：允许用户配置松开按键后多久才真正切断音频流，优化口语习惯。
